# AnimeCode 完整追番系统落地路线图

## 1. 总体目标

AnimeCode 的目标是从一个最小可用的番剧查询工具，逐步演进为完整追番系统。完整形态应覆盖：

1. 从 yuc 等网页数据源抓取番剧信息；
2. 提供当前季度、指定季度、周表、番剧详情等查询能力；
3. 向 Agent 暴露本地 Skill / Tool 能力；
4. 后续提供 HTTP 查询 API；
5. 支持缓存、本地番剧库和后台同步；
6. 支持用户追番订阅；
7. 支持基于播出时间的提醒；
8. 支持 QQ Bot 命令和主动提醒；
9. 支持观看入口、RSS 规则和 qBittorrent 下载状态管理。

整体原则：

- 查询优先，状态后置。
- 爬虫代码是确定性底层能力。
- Skill / Tool 是 Agent 调用爬虫能力的包装层。
- API 是系统对外服务能力出口。
- 后台、订阅、提醒、QQ Bot、RSS/qB 都依赖服务器和存储状态，应在查询能力稳定后逐步实现。

## 2. 模块拆分

| 模块 | 职责 | 依赖 | 需要数据库 | 需要服务器常驻 | 适合第一版 |
|---|---|---|---:|---:|---:|
| 数据模型与标准化模块 | 定义统一输出结构，标准化标题、季度、星期、播出时间 | 无 | 否 | 否 | 是 |
| yuc 网页抓取模块 | 抓取 yuc 当前季度、指定季度页面，并提取周表与番剧详情源记录 | 数据模型与标准化 | 否 | 否 | 是 |
| 本地 Agent Skill / Tool 模块 | 将已有 yuc 能力包装给 Agent 调用，不承载爬虫解析逻辑 | yuc 网页抓取 | 否 | 否 | 是 |
| 查询 API 模块 | 提供 HTTP 查询接口 | yuc 抓取或本地数据源 | 否 | 是 | 否 |
| 缓存 / 本地番剧库模块 | 缓存抓取结果，保存番剧目录与解析状态 | 查询能力 | 是 | 可选 | 否 |
| 后台同步模块 | 定时同步当前季度和下季度，记录失败状态 | 本地番剧库 | 是 | 是 | 否 |
| 订阅模块 | 添加追番、取消追番、查看我的追番 | 本地番剧库、用户模型 | 是 | 是 | 否 |
| 提醒模块 | 根据订阅和播出时间生成提醒，防重复提醒 | 订阅模块、后台任务 | 是 | 是 | 否 |
| QQ Bot 适配模块 | 接收 QQ 命令，调用核心 API，发送回复 | 查询、订阅、提醒 API | 是 | 是 | 否 |
| 观看入口与 RSS/qB 模块 | 管理 B 站入口、RSS 规则草稿、qB 下载状态 | 订阅、确认机制、qB 适配器 | 是 | 是 | 否 |

## 3. 阶段路线

### V1：查询 MVP，拆成 yuc 能力与 Skill 创建

目标是最小可用查询能力，不依赖数据库或服务常驻。

V1 分三步实现：

1. `V1-A0：数据模型与标准化`
   - 数据模型与标准化；
   - 外部数据源无关的统一输出结构；
   - 标题、季度、星期、播出时间归一化。
2. `V1-A：yuc 静态抓取`
   - yuc 网页抓取；
   - 当前季度、周表、搜索、详情的纯代码能力；
   - 调用标准化模块输出统一模型。
3. `V1-B：本地 Agent Skill / Tool 创建`
   - 复用 V1-A 的 yuc 能力；
   - 定义 Agent 可调用的工具入口；
   - 不在 Skill 内重复实现爬虫解析。

主要能力：

- 查询当前季度新番；
- 查询指定季度周表；
- 按星期查询番剧；
- 搜索番剧；
- 查询番剧基础详情。

### V2：查询 API

目标是把 V1 的本地查询能力开放为 HTTP 接口。

实现内容：

- FastAPI 项目骨架；
- 当前季度查询接口；
- 季度周表接口；
- 番剧搜索接口；
- 番剧详情接口。

说明：

- V2 仍可不依赖数据库；
- API 只调用确定性爬虫或标准化模块；
- 不处理用户订阅状态。

### V3：缓存 / 本地番剧库

目标是降低源站请求频率，并为后续订阅、提醒提供稳定数据基础。

实现内容：

- SQLite 存储；
- 番剧目录表；
- 季度同步状态；
- 抓取结果缓存；
- 解析失败日志。

说明：

- 查询优先读本地数据；
- 本地缺失或过期时再抓取 yuc；
- 失败时返回结构化错误，不生成猜测结果。

### V4：后台同步

目标是让系统可以自动维护本地番剧库。

实现内容：

- 当前季度定时同步；
- 下季度定时同步；
- 手动同步触发；
- 同步错误记录；
- 解析失败样本记录。

说明：

- 从此阶段开始需要服务器常驻；
- 后台任务不放在请求响应流程中。

### V5：订阅

目标是支持用户追番状态。

实现内容：

- 用户模型；
- 订阅模型；
- 添加追番；
- 取消追番；
- 查看我的追番。

规则：

- 同一用户对同一番剧只能有一条有效订阅；
- 取消追番使用软状态；
- 再次追番恢复已有订阅；
- 不在订阅阶段实现提醒发送。

### V6：提醒

目标是基于订阅和播出时间生成提醒事件。

实现内容：

- 提醒时间计算；
- 提醒日志；
- 防重复提醒；
- 提醒消息生成；
- 消息发送适配器接口。

说明：

- 第一版提醒可先 mock 发送；
- 真正发送到 QQ 放到下一阶段。

### V7：QQ Bot

目标是通过 QQ 命令使用核心系统能力。

实现内容：

- QQ Bot 适配层；
- 命令解析；
- 查询命令；
- 追番命令；
- 我的追番命令；
- 提醒消息发送。

边界：

- QQ Bot 不直接写数据库；
- QQ Bot 不直接抓 yuc；
- QQ Bot 不直接访问 qBittorrent；
- QQ Bot 只调用核心 API。

### V8：观看入口与 RSS/qB

目标是补齐观看和下载自动化能力。

实现内容：

- B 站搜索入口；
- 手动观看链接绑定；
- RSS 规则草稿；
- 用户确认后创建 RSS/qB 规则；
- qB 下载状态查询；
- 下载状态展示。

安全边界：

- Agent 不能直接操作 qB；
- qB 密码不能暴露给 Agent；
- RSS/qB 创建必须走确认流程；
- 删除、批量操作、修改下载路径属于高风险操作。

## 4. 推荐实现顺序

```text
数据模型与标准化
→ yuc 网页抓取
→ 本地 Agent Skill / Tool
→ 查询 API
→ 缓存 / 本地番剧库
→ 后台同步
→ 订阅
→ 提醒
→ QQ Bot
→ 观看入口与 RSS/qB
```

第一阶段只做查询相关能力。涉及用户状态、后台任务、主动通知和下载器管理的能力全部后置。

## 5. 分层原则

### 爬虫层

爬虫层负责确定性抓取和解析，不依赖 Agent 判断页面内容。

### Skill / Tool 层

Skill / Tool 层负责把爬虫能力包装成 Agent 可调用的输入输出，不保存业务状态。

### API 层

API 层负责提供系统能力出口，供 Web、QQ Bot、Agent Tool 或其他客户端调用。

### 存储层

存储层从缓存和本地番剧库开始，之后承载用户订阅、提醒日志、RSS 规则等状态。

### 后台层

后台层负责同步、提醒扫描、下载状态检查等长期任务，不应塞进普通查询请求。

## 6. 当前默认决策

- 第一版先实现 yuc 能力，再创建本地 Skill / Tool 包装，不把两者混成一个模块。
- 第一版不做 HTTP API。
- 第一版不引入数据库。
- 第一版只支持 yuc 数据源。
- Bangumi、AniList 作为后续补充数据源。
- 缓存、本地库、后台同步、订阅、提醒、QQ Bot、RSS/qB 都在后续阶段实现。
